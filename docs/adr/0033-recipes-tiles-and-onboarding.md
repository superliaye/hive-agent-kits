# Recipes, Tiles, and Onboarding

status: proposed
relates-to: ADR-0024, ADR-0026, ADR-0029, ADR-0031, ADR-0032

## What this ADR records

Hive syncs, lists, and distributes agent capability Sources of every common
shape, not only Sources written in Hive's capability format. A user picks a
known repository from a shelf of **Tiles**, or pastes any repository link. Hive
then installs and uninstalls what that repository ships, on Claude Code and
Codex, the way the repository tells a user to do it by hand.

Three repositories show the roles:

- **my-agent-kits**: a personal capability kit that holds working and experimental
  Capabilities.
- **yestack**: a shared plugin with a high bar. Content goes there only when its
  owner promotes it.
- **hive-agent-kits**: the app that syncs, lists, and distributes Sources.

## Decision

- **A Recipe turns a Source into Capabilities.** Every Source kind (git, working
  tree, Starter) syncs through one path. Hive lists the tree, a Recipe recognizes
  it through a small query interface, and Hive copies only the files the Recipe
  asks for into the Mirror. So a large repository fits when its skills are small.
  The Mirror's identity is a digest of what was written plus the Recipe. Hive tries
  its generic Recipes in a fixed order and uses the first that recognizes the tree:
  1. **Capability kit**: the tree has `capabilities/` (ADR-0024).
  2. **Plugin marketplace for both CLIs**: Claude Code and Codex marketplace files
     that list plugins under one name, at the root of a whole git repository
     (ADR-0031). Hive reads only the names, so any plugin `source` form is
     accepted. Each plugin installs and uninstalls with each CLI's plugin commands
     (ADR-0032).
  3. **Published skills**: skill folders found the way `npx skills add` finds them.
     A `SKILL.md` at the root is one skill. Otherwise the search covers the root's
     children, `skills/` and its curated folders, the agent project skill folders,
     and the skill paths a Claude marketplace declares. If those hold none, a
     deeper search runs. A skill needs a `name` and `description`, and a skill
     marked `metadata.internal` is skipped. A skill whose files reference
     `${CLAUDE_PLUGIN_ROOT}` needs a plugin runtime and is skipped too. Hive
     deploys each skill natively and verbatim: files keep their bytes and exec
     bits, and none of a kit's include expansion applies, so no external
     installer runs.
  4. **Single-CLI plugin marketplace**: only one of the two marketplace files lists
     plugins, and the plugins target that CLI.

  A pattern for both CLIs wins over a single-CLI form of the same content, so a
  repository that ships skills and a Claude-only marketplace serves Codex too. A
  tree no Recipe recognizes fails Sync with `not_recognized` and a reason naming
  what each Recipe looked for.
- **Generic patterns apply to every Source; repo-specific recipes only to
  Tiles.** A repo-specific recipe covers a repository no pattern fits, such as
  one whose skills are generated by its own `./setup --host <cli>`. Such a recipe
  may run that repository's scripts, so only Tiles can carry one: Onboarding
  reviews the recipe, and Hive ships it (ADR-0034). A Source runs its Tile's
  Recipe exactly when its locator is that Tile's locator, and never falls back to
  the generic patterns. So a pasted link equal to a Tile's becomes that Tile, and
  any other link gets the generic patterns, which never run repository code.
- **The Recipe sets the Selection unit.** A capability kit, a collection of
  independent skills, and a plugin marketplace let the user pick Capabilities;
  each plugin already installs whole through its CLI. A repo-specific recipe
  installs the Source whole. A Tile may narrow a collection to whole when its
  skills work together (HyperFrames). The daemon owns the rule: a change to one
  Capability of a whole Source applies to all of them, and every Selection read
  closes a partial unit, so the Selection API, the Overview, and Deploy agree.
- **Tiles are curated Sources shipped with Hive.** A Tile records a Source Locator,
  a label and description, its Recipe, and its Selection unit. The Starter Source
  is the first Tile. Selecting a Tile adds the Source. Tiles track the
  repository's default branch, like any git Source. A Source's Tile is derived
  from its locator, never stored, so Sources added before a Tile existed match it
  too.
- **Onboarding is a development step in this repository.** For a new repository,
  Onboarding reads the install and uninstall steps its documentation recommends
  for each CLI. It matches them to a generic pattern, generalizes a new pattern
  when the shape is common, or writes a repo-specific recipe. It verifies install
  and uninstall on each CLI in throwaway homes, then adds the Tile and records its
  fixture: the answers recognition got from the repository, replayed by a test so
  a change in how Hive recognizes a known repository fails before it ships. The
  procedure is `.claude/skills/onboard-source`. End users never run Onboarding.
- **Kits stop wrapping upstream repositories.** A bundle or plugin pointer in a
  kit that only wraps an upstream repository moves to a Tile. The bundle kind
  stays in the capability format for kits that still use it (ADR-0026).

## Trade-offs

- Published-skills discovery copies the `skills` CLI's rules (version 1.7.2),
  which can change between its versions. `recipe-lever --compare-npx` diffs Hive's
  result against the CLI, and each Tile's fixture test catches a drift in Hive.
- Native skill deploy skips the external installer, so a step the installer adds
  beyond copying folders is lost. Onboarding finds such repositories, and they
  get a repo-specific recipe.
- Tracking the default branch means a Tile changes when its upstream changes.
  Running a repo-specific recipe's scripts from a moving branch trusts the
  upstream with each Sync.
- An unrecognized pasted link fails at Sync with a reason rather than guessing.
